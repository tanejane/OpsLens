# Data coverage and reasoning audit

Reviewed 5 November 2026. **OpsLens can explain bounded accounting contributions and selected descriptive outcomes. It cannot establish general business root causes.** Many useful input types exist, but presence, SQL access, relationship validation and an executable investigation route are four different levels of support.

This review inspected loader manifests and view definitions, CSV headers (not customer records), semantic and metric catalogs, relationship auditors, MCP policy/tools, evidence SQL, finance/refund/seller/review executors, Gemini prompts, runtime dispatch and result serialization. Historical live evidence comes from `RELEASE_READINESS.md` and its retained benchmark artifacts. No new database or Gemini verification was performed for this audit. Fixture ground truth is not business evidence and must remain outside runtime reasoning.

### What “validated relationship” means here

`phase4b42_relationship_auditor.py` checks parent uniqueness, nulls and orphans in the correct FK direction. Its `STRUCTURALLY_VERIFIED` result explicitly does not authorize a measure or prove safe aggregation. The semantic map has declared coverage fields, including null coverage; metadata is not a current live certificate. Relationship contracts allow bounded seller order counts and incident-category margin, not arbitrary joining.

Critical rules: preaggregate reviews/returns/payments before order joins; never sum order finance after a one-to-many item join; never sum campaign-day spend across order rows; retain unknown and multi-seller partitions; verify effective-date cost matching without overlapping intervals. Shared order IDs permit cohort analysis but do not make finance, placed-order, reviewed-order and delivery-eligible populations equal. Prior live reconciliation found 6,728 placed versus 6,694 financially represented orders in February 2018 and 7,211 versus 7,188 in March. Those historical checks do not certify all periods or relationships.

## Reasoning, routing and error-handling findings

1. **Gemini is an interpreter/selector, not an open-ended analyst.** `phase4c27a_interpreter.py` restricts intent/metric/category extraction and independently validates proposals. `phase5_1_explanation.py` explicitly forbids hypotheses/recommendations/prose and selects exact evidence-reference templates only after executable results. This protects figures but explains why insufficient-evidence answers can be unhelpful. Do not remove these restrictions wholesale.
2. **Accounting hypotheses are not root causes.** `phase4c5_hypotheses.py` correctly ranks reconciled accounting movements and labels them noncausal. Its generic next-validation instruction lacks the concrete data and falsification criteria a business analyst needs. Keep these measured movements separate from general possibilities.
3. **Catalogs disagree with runtime coverage.** The MCP metric catalog lists eight high-level metrics; downstream contracts define more precise product/delivery/review measures. `phase4c8_capabilities.py` still labels delivery/review diagnostics not connected despite later executors. Historical SQL comments also say not approved, whereas current policy and provisioning expose those views. Do not change permissions based on comments or infer all capabilities from a catalog entry.
4. **Provider outages suppress otherwise useful behavior.** `phase5_1_unified.py` returns `INTERPRETER_UNAVAILABLE` on generic provider exceptions rather than invoking the existing recovery path. The incident gateway deliberately does not repair that status. Refund period extraction can propagate an error to HTTP 503. Preserve outage visibility; a future bounded fallback must rerun original-input validation and must not turn malformed model output into trusted execution.
5. **Internal finance subquestions unnecessarily depend on a model when enabled.** `scripts/phase5_1_playground.py` already uses `CompiledComparisonInterpreter` for deterministic internally generated month comparisons when disabled. Enabled mode uses the model instead. Reusing the deterministic compiler for these particular trusted generated questions is promising, but requires tests for each caller and ambiguity checks before changing dispatch.
6. **Normal explanation payloads exceed what selection needs.** `select_explanation` forwards nested metric/premise/evidence context; the selector contract only chooses labels/references. The restricted benchmark adapter removes values and replaces internal questions, so its failures cannot be cleanly attributed to the default prompts. Recommend a separately tested minimal production selection payload, without weakening validators or authorizing new external transmission.
7. **Evidence-gap requirements describe unavailable proof, not necessarily absent datasets.** Existing aggregate metrics may exist while requested attribution does not. Use field/relationship-specific wording. Avoid claiming “no data” when the missing piece is governance, linkage or observation horizon.

The retained authorized live benchmark scored 6/7 core versus deterministic 7/7, with eight provider failures among 19 calls and one incident HTTP 503. This is historical restricted-input live evidence, not new verification or a population accuracy estimate. No unsupported causal certainty was flagged by its bounded structured checks; no incident mechanism was independently verified.

## Minimal change implemented

`agent/business_hypotheses.py` adds static, domain-specific possibilities with `UNVERIFIED_HYPOTHESIS`, `general_business_knowledge_not_case_evidence`, missing evidence, and checks that could support or weaken each possibility. `phase5_3c_incident_gateway.py` attaches at most three under `unverified_hypotheses` only when it already returns `ACTIONABLE_EVIDENCE_GAP`. This is a deterministic fallback, not a new Gemini prompt or analytical executor. It does not inspect fixture truth, echo model/user prose, fabricate observations, query data or alter measured outputs, ambiguity/policy refusals, provider-outage status, or SQL permissions.

The lossless v1 result contract retains the additive field. Frontend rendering of this new field has not been implemented or claimed: it is available in the canonical API record. Broader Gemini selection and user-facing display remain recommendations. Existing measured `hypotheses` are deliberately not mixed with these unverified possibilities.

Regression tests in `scripts/test_business_hypotheses.py` cover no-tool evidence gaps, explicit uncertainty and missing-evidence checks, canonical transport, preservation of measured/clarification/unsafe/outage responses, allowlisting, bounded output and mutation isolation.
